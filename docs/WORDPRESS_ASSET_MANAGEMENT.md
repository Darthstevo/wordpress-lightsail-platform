# WordPress Asset Management Strategy

## Overview

This document explains the recommended approach for managing WordPress code, themes, plugins, and media assets in a production environment.

## Storage Strategy

### What Goes Where

| Asset Type         | Storage                       | Why                                          |
| ------------------ | ----------------------------- | -------------------------------------------- |
| **WordPress Core** | Git Repository                | Version control, rollback, CI/CD             |
| **Custom Themes**  | Git Repository                | Track changes, code review, deploy via CI/CD |
| **Custom Plugins** | Git Repository                | Version control, testing, security auditing  |
| **Configuration**  | Ansible Variables (encrypted) | Infrastructure as Code, secret management    |
| **Media Uploads**  | S3 (via plugin)               | Scalability, CDN integration, cost-effective |
| **Backups**        | S3                            | Disaster recovery and operational resilience |

## Deployment Models

### Model 1: Fresh Installation (Recommended for New Sites)

**Use Case:** Starting a new WordPress site from scratch

**Process:**

```bash
1. Run the Provision + Configure workflow with default settings
2. WordPress installs clean
3. Access https://yourdomain.com/wp-admin/install.php
4. Complete WordPress setup wizard
5. Install themes/plugins via WP Admin or commit to Git
6. Configure S3 media offload plugin
```

**Pros:**

- ✅ Clean slate, no legacy issues
- ✅ Latest WordPress version
- ✅ Full control over configuration
- ✅ No migration complexity

**Cons:**

- ❌ Manual theme/plugin installation
- ❌ Content must be created from scratch

### Model 2: Two-Repository App Delivery (Recommended for Teams)

**Use Case:** Development workflow with version-controlled themes/plugins

**Setup:**

```
my-wordpress-repo/
├── .github/workflows/         # CI/CD for theme/plugin deployment
├── themes/
│   └── my-custom-theme/
├── plugins/
│   └── my-custom-plugin/
├── composer.json              # PHP dependency management
└── package.json               # Frontend build tools
```

**WordPress Structure:**

```
/var/www/html/
├── wp-admin/                  # WordPress core (updated via wp-cli)
├── wp-includes/               # WordPress core
├── wp-content/
│   ├── themes/                # Deployed from Git
│   ├── plugins/               # Deployed from Git
│   └── uploads/               # Offloaded to S3
├── wp-config.php              # Generated by Ansible template
└── .htaccess
```

**Deployment Pipeline:**

```bash
1. Fresh WordPress install via workflow
2. Git clone custom themes/plugins to /var/www/html/wp-content/
3. Run composer install for PHP dependencies
4. Run npm install && npm run build for frontend assets
5. Configure S3 offload plugin
6. Validate deployment and activate desired theme/plugins
```

**Pros:**

- ✅ Version control for custom code
- ✅ Automated deployments
- ✅ Separate staging/production environments
- ✅ Code review process
- ✅ Rollback capability

**Cons:**

- ❌ More complex setup
- ❌ Requires CI/CD pipeline
- ❌ Team coordination needed

## Media Upload Management

### Option 1: S3 Offload Plugin (Recommended)

**Plugin:** WP Offload Media Lite (free) or Pro (paid)

**Configuration:**

```php
// wp-config.php additions
define('AS3CF_SETTINGS', serialize([
    'provider' => 'aws',
    'access-key-id' => 'AKIAIOSFODNN7EXAMPLE',
    'secret-access-key' => 'wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY',
    'bucket' => 'my-wordpress-media',
    'region' => 'us-east-1',
    'copy-to-s3' => true,
    'serve-from-s3' => true,
    'remove-local-file' => true,  // Save disk space
]));
```

**Benefits:**

- ✅ Automatic upload to S3
- ✅ CDN integration (CloudFront)
- ✅ Reduced disk usage on Lightsail
- ✅ Better performance
- ✅ Easier backups (S3 versioning)

**Cost:**

- S3 storage: ~$0.023/GB/month
- Data transfer: $0.09/GB (out to internet)
- CloudFront: $0.085/GB (first 10TB)

**Example:** 10GB media + 100GB transfer = ~$9.50/month

### Option 2: Local Storage Only

**Use Case:** Small sites (<1GB media), budget-constrained

**Pros:**

- ✅ Simple setup
- ✅ No additional costs
- ✅ No plugin dependencies

**Cons:**

- ❌ Limited by Lightsail disk space
- ❌ No CDN benefits
- ❌ Harder to backup
- ❌ Slower for global users

## Backup Strategy

### Automated Backups with Ansible

Create scheduled backup playbook:

```yaml
# ansible/playbooks/backup.yml
---
- name: Backup WordPress to S3
  hosts: lightsail
  become: true
  tasks:
    - name: Dump database
      community.mysql.mysql_db:
        name: "{{ wp_db_name }}"
        state: dump
        target: /tmp/wordpress-{{ ansible_date_time.epoch }}.sql
        login_user: "{{ wp_db_user }}"
        login_password: "{{ wp_db_password }}"

    - name: Compress database dump
      ansible.builtin.command:
        cmd: gzip /tmp/wordpress-{{ ansible_date_time.epoch }}.sql

    - name: Archive wp-content
      community.general.archive:
        path: /var/www/html/wp-content
        dest: /tmp/wp-content-{{ ansible_date_time.epoch }}.tar.gz

    - name: Upload to S3
      amazon.aws.s3_object:
        bucket: my-wordpress-backups
        object: "{{ item }}"
        src: "/tmp/{{ item }}"
        mode: put
      loop:
        - "wordpress-{{ ansible_date_time.epoch }}.sql.gz"
        - "wp-content-{{ ansible_date_time.epoch }}.tar.gz"

    - name: Clean up local backups
      ansible.builtin.file:
        path: "/tmp/{{ item }}"
        state: absent
      loop:
        - "wordpress-{{ ansible_date_time.epoch }}.sql.gz"
        - "wp-content-{{ ansible_date_time.epoch }}.tar.gz"
```

**Schedule with GitHub Actions:**

```yaml
# .github/workflows/backup-wordpress.yml
name: WordPress Backup

on:
  schedule:
    - cron: "0 2 * * *" # Daily at 2 AM UTC
  workflow_dispatch: # Manual trigger

jobs:
  backup:
    runs-on: ubuntu-latest
    steps:
      - name: Run backup playbook
        run: ansible-playbook -i inventory/prod.ini playbooks/backup.yml
```

### Backup Retention Policy

**Recommended S3 lifecycle rules:**

```json
{
  "Rules": [
    {
      "Id": "DailyBackupRetention",
      "Status": "Enabled",
      "Prefix": "wordpress-",
      "Transitions": [
        {
          "Days": 30,
          "StorageClass": "STANDARD_IA"
        },
        {
          "Days": 90,
          "StorageClass": "GLACIER"
        }
      ],
      "Expiration": {
        "Days": 365
      }
    }
  ]
}
```

**Cost example:**

- Daily backups: 1GB each
- 30 days Standard: 30GB × $0.023 = $0.69/month
- 60 days IA: 60GB × $0.0125 = $0.75/month
- 275 days Glacier: 275GB × $0.004 = $1.10/month
- **Total: ~$2.54/month** for 1 year of backups

## Version Control Strategy

### Recommended Git Workflow

**Repository Structure:**

```
wordpress-lightsail-platform/
├── .github/workflows/         # Infrastructure + deployment CI/CD
├── ansible/                   # Configuration management
├── terraform/                 # Infrastructure as Code
├── cdk/                       # Observability stacks
├── wordpress/                 # Custom WordPress code (optional)
│   ├── themes/
│   │   └── my-theme/
│   ├── plugins/
│   │   └── my-plugin/
│   └── mu-plugins/           # Must-use plugins
└── docs/
```

**What to Commit:**

- ✅ Custom themes (if not using commercial theme)
- ✅ Custom plugins
- ✅ Must-use plugins
- ✅ Configuration files (wp-config template)
- ✅ Deployment scripts

**What NOT to Commit:**

- ❌ WordPress core files
- ❌ Third-party themes/plugins (use composer instead)
- ❌ Uploads/media
- ❌ Database dumps
- ❌ wp-config.php with credentials
- ❌ .htaccess (generated)

### Using Composer for WordPress

**composer.json example:**

```json
{
  "name": "my-org/wordpress-site",
  "repositories": [
    {
      "type": "composer",
      "url": "https://wpackagist.org"
    }
  ],
  "require": {
    "php": ">=8.0",
    "johnpbloch/wordpress": "^6.4",
    "wpackagist-plugin/wordpress-seo": "^21.0",
    "wpackagist-plugin/wordfence": "^7.11",
    "wpackagist-theme/twentytwentyfour": "^1.0"
  },
  "extra": {
    "wordpress-install-dir": "wordpress",
    "installer-paths": {
      "wp-content/plugins/{$name}/": ["type:wordpress-plugin"],
      "wp-content/themes/{$name}/": ["type:wordpress-theme"]
    }
  }
}
```

**Benefits:**

- ✅ Version-locked dependencies
- ✅ Reproducible deployments
- ✅ Easy updates (`composer update`)
- ✅ No vendor code in Git

## Security Best Practices

### File Permissions

```bash
# WordPress root
sudo chown -R www-data:www-data /var/www/html
sudo find /var/www/html -type d -exec chmod 755 {} \;
sudo find /var/www/html -type f -exec chmod 644 {} \;

# wp-config.php (sensitive)
sudo chmod 640 /var/www/html/wp-config.php

# wp-content/uploads (writable)
sudo chmod 755 /var/www/html/wp-content/uploads
```

### S3 Bucket Security

**Bucket policy for media offload:**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-wordpress-media/*"
    },
    {
      "Sid": "WordPressUpload",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::ACCOUNT:user/wordpress-uploader"
      },
      "Action": ["s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::my-wordpress-media/*"
    }
  ]
}
```

**IAM policy for WordPress:**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::my-wordpress-media"
    },
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::my-wordpress-media/*"
    }
  ]
}
```

## Launch Checklist

### Pre-Launch

- [ ] Confirm domain and DNS values in `ansible/group_vars/wordpress.yml`
- [ ] Commit themes/plugins to the site repository
- [ ] Verify GitHub Actions secrets and role ARNs
- [ ] Validate HTTPS certificate domain/SAN configuration
- [ ] Review plugin/theme compatibility with target WordPress/PHP versions

### Deployment

- [ ] Run `Provision + Configure (OpenTofu + Ansible)` workflow
- [ ] Verify WordPress installer loads at `/wp-admin/install.php`
- [ ] Activate theme/plugins and test core functionality
- [ ] Verify uploads path and media behavior

### Post-Launch

- [ ] Update site URL in WordPress settings
- [ ] Regenerate permalinks (Settings → Permalinks → Save)
- [ ] Clear all caches
- [ ] Test forms and contact functionality
- [ ] Check SSL/HTTPS working
- [ ] Verify email sending works
- [ ] Test user login/authentication
- [ ] Monitor error logs for 24 hours
- [ ] Enable recurring backup operations
- [ ] Monitor CloudWatch alarms for 24 hours

- **Wordfence Security** - Firewall, malware scanning
- **UpdraftPlus** - Automated backups to S3
- **WP Offload Media** - Media upload to S3/CloudFront
- **WP Super Cache** or **W3 Total Cache** - Page caching

### Optional but Useful

- **Yoast SEO** - SEO optimization

- **Health Check** - PHP/WordPress debugging

## Troubleshooting

### Common Issues

**Issue: Upload size limit too small**

```php
// wp-config.php
@ini_set('upload_max_filesize', '64M');
@ini_set('post_max_size', '64M');
@ini_set('max_execution_time', '300');
```

**Issue: Memory limit exhausted**

```php
// wp-config.php
define('WP_MEMORY_LIMIT', '256M');
```

**Issue: S3 uploads failing**

```bash
# Check IAM permissions
# Verify S3 bucket policy
# Check plugin configuration
# Test AWS credentials with AWS CLI
```

**Issue: Database connection errors**

```bash
# Verify wp-config.php database credentials
# Check MySQL is running: systemctl status mysql
# Test connection: mysql -u user -p database
# Review error logs: /var/log/mysql/error.log
```

## Summary

**For Fresh Sites:**

- Deploy using the default platform workflow
- Use S3 offload plugin for media
- Version control custom themes/plugins
- Automate backups to S3

**For Production:**

- Daily automated backups to S3
- S3 lifecycle policies for cost optimization
- Monitoring and alerting (already configured)
- Regular WordPress/plugin updates
